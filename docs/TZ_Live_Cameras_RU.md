# ТЗ: live RTSP-камеры, узлы обработки, админка

Статус: в работе с 02.10.2026. Решения согласованы с пользователем (ответы на 16 вопросов).
Документ описывает **целевое поведение этого этапа**, а не будущий продукт.

## 1. Цель

Камера заклада может быть живым RTSP-источником. Система сама:

- пишет основной поток в архив, хранит **24 часа** на узле, который обслуживает камеру;
- почти в реальном времени (обновление ~5 с) находит людей (YOLO11s + ByteTrack) и столики;
- считает метрики по типу камеры и хранит агрегаты **бессрочно** в Mongo;
- сырые треки хранит **7 дней**, чтобы после смены разметки пересчитать метрики задним числом.

Загрузка видеофайлов остаётся вторым типом источника (`source: "upload"`).

## 2. Архитектура

```
                ┌────────────────────── главный сервер ───────────────────────┐
 браузер ──────▶│ frontend :5173 ──/api──▶ api :4000 ──▶ mongo                │
   ▲  WebRTC     │                         │  ▲  ▲                            │
   └─────────────┤ mediamtx-hub ◀──auth────┘  │  │ HTTPS + WS (токен узла)    │
     (UDP 8189)  │   ▲ RTSP publish           │  │                            │
                 └───┼────────────────────────┼──┼────────────────────────────┘
                     │ (только пока смотрят)  │  │
                ┌────┴──── узел обработки (Docker, CPU или NVIDIA GPU) ───────┐
                │ camera-node: агент + YOLO ─┘  │                             │
                │   ▲ RTSP (локально)            │                             │
                │ node-mediamtx: тянет камеру, пишет архив 24 ч, playback     │
                └────┬────────────────────────────────────────────────────────┘
                     │ RTSP (main + sub)
                  камера
```

- **Главный сервер**: `mongo`, `api`, `frontend`, `mediamtx` (hub: только раздача live-видео браузеру).
- **Узел** (`deploy/node/`): `camera-node` (Python-агент + YOLO) и `node-mediamtx`. Узлу не нужен публичный IP:
  всё общение инициирует узел (HTTPS-запросы + WebSocket к API, RTSP-публикация на hub).
- Локальная разработка: главный compose поднимает и локальный узел (`slug: local`, токен из `.env`).
- Узел обрабатывает и live-камеры, и загруженные файлы (заменяет прежний `video-worker`).
- Mongo наружу не открывается; узел не имеет прямого доступа к БД.

### Подключение узла

1. Админ в «Адмінка → Вузли» жмёт «Додати вузол» → получает токен `vfn_<id>_<secret>` (показывается **один раз**,
   в БД хранится sha256) и готовую команду запуска (`deploy/node`, `.env` с `VENUEFLOW_URL` и `NODE_TOKEN`).
2. Узел шлёт heartbeat каждые 5 с: железо (CPU/RAM/GPU/диск), состояние каждой камеры (fps, ошибка, последний кадр).
   В ответ получает конфиг: назначенные камеры с расшифрованными RTSP URL (только по HTTPS), адрес hub.
3. WebSocket `/api/node/ws` — команды от API: `watch` (кто-то смотрит live → публиковать видео и рамки),
   `probe` (проверка подключения), `archive.list`, `archive.clip`, `tables.detect`, `snapshot`.
4. Токен можно перевыпустить или узел отключить — старый токен сразу перестаёт работать.

### Распределение камер

Новая RTSP-камера автоматически назначается на наименее загруженный online-узел (с учётом `maxCameras`).
Нет свободного узла → камера в статусе «очікує вузол», назначится, когда узел появится. Админ может перенести
камеру вручную. Автоматического failover нет (архив остаётся на старом узле).

## 3. Камера

### Добавление (мастер)

1. **Підключення**: назва, RTSP-адреса, логін, пароль, субпотік (для Dahua/Imou `subtype=0` → `subtype=1`,
   для Hikvision `…/101` → `…/102` подставляется автоматически). «Перевірити» → узел открывает поток и возвращает
   кадр, кодек, разрешение, fps для main и sub. Понятные ошибки: неверный пароль, таймаут, нет узла.
2. **Тип**: Indoor / Outdoor / Hybrid с иллюстрацией, что будет считаться.
3. **Розмітка** на реальном кадре (можно пропустить и вернуться).

### Секреты

RTSP URL и пароль шифруются AES-256-GCM ключом `CAMERA_SECRET_KEY` (только `.env` главного сервера).
Клиенту API отдаёт хост/путь и логин, пароль — никогда. В логи URL с паролем не попадает.

### Потоки

| Поток | Назначение |
|---|---|
| main (у тестовой камеры HEVC 1280×720 25 fps) | архив 24 ч (без аудио), снимок для разметки, детект столиков |
| sub (H.264 640×480 15 fps) | YOLO-анализ (~5 fps), live-видео в браузере (WebRTC) |

Если субпотока нет — анализ и live идут по main. **Аудио не пишем и не транслируем** (приватность).

## 4. Типы камер и метрики

| Тип | Разметка | Метрики |
|---|---|---|
| **Indoor** | зона залу (необов'язково, иначе весь кадр), столики | хитмап, люди зараз / пік / середнє, зайнятість столиків, середній час за столиком |
| **Outdoor** | лінія дверей з напрямком «всередину» + зона тротуару | зайшло, вийшло, пройшло повз, конверсія входу |
| **Hybrid** | поріг (лінія дверей) + проріз дверей (полігон, там видно вулицю) + зона залу + столики | зайшло, пройшло повз, конверсія + все метрики Indoor для залу |

Определения (считает API из треков, одна реализация на JS):

- **Зайшло / вийшло** — пересечение линии дверей внутрь / наружу (гистерезис 1.5% кадра).
- **Пройшло повз** — завершённый трек, который побывал в зоне тротуара (outdoor) или в проёме двери (hybrid, ≥ 60% точек
  трека в проёме) и не пересёк линию внутрь. Конверсия = зайшло / (зайшло + пройшло повз).
- **Люди в залі** — треки, чья точка ног внутри зоны зала (или всего кадра минус проём/тротуар).
- **Столик зайнятий** — точка ног человека внутри расширенного полигона стола; сессия ≥ 60 с, разрывы < 30 с склеиваются.
- **Хитмап** — людино-секунди в сетке 48×27 (без проёма двери у hybrid).

Столики: узел раз в 5 мин (и по кнопке) ищет `dining table` (COCO) на кадре main-потока, кластеризует по IoU
и отдаёт кандидатов. Владелец принимает/удаляет/дорисовывает столики в редакторе. Считаем только подтверждённые.

## 5. Данные

| Коллекция | Что | Срок |
|---|---|---|
| `livetracks` | точки ног трека `[offsetSec, x, y]` 2 Гц | TTL 7 дней |
| `camerahours` | по камере и часу: покрытие по минутам, входы/выходы/проходы/люди по минутам, хитмап, столики | бессрочно |
| `nodes` | узлы, железо, статистика | — |
| архив видео | fMP4 сегменты 10 мин на диске узла | 24 ч (MediaMTX `recordDeleteAfter`) |

- **Покрытие** (сколько секунд камера реально анализировалась) хранится отдельно: если камера была offline,
  в графиках **пробел, а не ноль**.
- Rollup: загрузка треков помечает затронутые часы `dirty`, фоновый цикл API пересчитывает их каждые ~10 с.
- Смена разметки → `markupVersion++` → пересчёт всех часов за 7 дней (дальше треков нет; UI честно пишет,
  что более старые часы посчитаны по прежней разметке).

## 6. UI (упор на визуал)

- **Камери**: сетка карточек с живым превью, статус (online/connecting/offline/очікує вузол + причина), тип, fps.
- **Камера**: вкладки «Наживо» (WebRTC + canvas-оверлей: рамки людей с ID, следы, зоны, столики цветом
  зайнятості, счётчики), «Архів» (таймлайн 24 ч с плотностью людей и отметками входов, клик → фрагмент),
  «Розмітка» (инструменты по типу камеры, перетаскивание точек, столики), «Налаштування».
- **Головна**: полоса «Зараз» по live-камерам, период (сьогодні / вчора / 7 / 30 днів), KPI по типу камеры,
  трафик «зайшло vs пройшло повз», люди по часам, зайнятість столиків (сетка столики × години), хитмап.
- **Адмінка** (роль admin): вузлы с метриками железа и fps, добавление/перевыпуск токена/отключение, назначение камер.
- Архив HEVC: если браузер не умеет HEVC, узел перекодирует фрагмент в H.264 (NVENC на GPU, иначе libx264).

## 7. Вне рамок этапа

ONVIF/автопоиск, PTZ, алерты, распознавание лиц и повторных гостей, POS, failover камер между узлами,
реестр Docker-образов (узел собирается из репозитория).

## 8. Проверка

- Unit: rollup/метрики по типам (JS), трекбук/кластеризация столов (Python), шифрование, токены узлов.
- E2E: эмулированная камера (`fake-camera`, профиль compose `dev-camera`) крутит `people-detection.mp4` по RTSP →
  live-камера outdoor с линией `y=0.85` → входы растут; реальная камера (hybrid) — подключение, live, архив, столики.
